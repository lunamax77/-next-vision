# 対外的な実行を伴う自動化の作り方(二段階承認ゲート)

会社憲章 第4-2項(対外行為・重要決定には代表の承認が必要)を、**自動化スクリプトの
実装レベル**でどう守るかの具体パターン。`browser`スキルのテンプレートで確立し、
実際にローカルのテストフォームで動作検証済み。フォーム送信に限らず、
「実行すると取り消せない/外部に影響する」操作全般に応用できる。

## 課題

自動化スクリプトに「入力して送信するところまで」を書かせると、承認を待たずに
そのまま送信まで実行してしまう恐れがある。かといって、送信部分を別スクリプトに
分けると二度手間で、入力内容の受け渡しも面倒になる。

## 解法: 同じスクリプトの中に、実行を分ける「スイッチ」を埋め込む

- スクリプトの冒頭で、環境変数などのフラグ(例: `SUBMIT`)を読む。
- **フラグが立っていない(既定)ときは、入力・準備までを行い、対外的な実行
  (送信ボタンを押す、APIを叩く、ファイルを提出する、等)の直前で止める。**
  その代わり、「これから何を実行する予定か」(送信予定の値、スクリーンショット等)を
  明示的に出力し、それを代表に提示して承認を求める。
- **フラグが立っているときだけ、最後の一歩(対外的な実行)を実行する。**
- どちらのケースでも、実行前・実行後の状態がわかる記録(スクリーンショット、
  ログ等)を残す。

```
[既定]      入力・準備 → 「これを送ります」を提示 → 【ここで止まる】
                                    ↓ 代表の承認
[フラグON]  入力・準備 → 対外的な実行(送信・投稿・提出など)
```

## 実装した際の要点

- フラグの初期値は**必ず「実行しない」側**にする。付け忘れても安全な方に倒れる設計。
- 「これから何を実行する予定か」は、スクリーンショットや構造化データ(JSON等)など、
  代表が中身を確認しやすい形で出す。ログの生の断片だけでは判断しづらい。
- 承認を得て2回目(フラグON)を実行するときも、**同じスクリプトを再実行するだけ**で
  済むようにしておくと運用が楽(別スクリプトを新たに用意しない)。
- 認証情報(パスワード・APIキー等)は、このゲートとは別に、常に環境変数経由で渡し、
  スクリプトやログに書き残さない。

## 応用できる場面

ブラウザ操作(フォーム送信・予約・発注)に限らず、メール送信、SNS投稿、
支払い実行、外部APIへの書き込みなど、「代表の承認を経てから対外的に実行したい」
自動化全般に、同じ二段階構造をそのまま当てはめられる。
