# ブラウザ自動化(Playwright)の環境依存の注意点

`browser`スキルを作って検証する過程で実際に踏んだ問題と対処。**環境(クラウドの
サンドボックスか、代表PC上のローカル実行か)によって当てはまるかどうかが変わる**
ので、症状が出たときにここを疑う、という位置づけ。

## 1. ブラウザ本体とライブラリのバージョンを合わせる

Playwrightは、ライブラリのバージョンごとに「対応するブラウザ本体のバージョン」が
決まっている。実行環境にあらかじめブラウザ本体(Chromium等)が同梱されている場合、
ライブラリを最新版で入れるとバージョンが噛み合わず、「ブラウザをダウンロードして
ください」というエラーで起動に失敗する。

- 対処: 同梱されているブラウザのバージョンを確認し、それに対応するライブラリの
  バージョンを**明示的に指定して**インストールする(最新版を無条件に入れない)。
- 同梱ブラウザの実体(実行ファイルのパス)を確認しておくと、バージョンの対応関係を
  調べる手がかりになる。

## 2. 外向き通信がプロキシ経由の環境での落とし穴

クラウドの実行環境では、外向きの通信がプロキシ(中継サーバー)を通る設定に
なっていることがある。この状態でbrowserライブラリを素朴に起動すると、
**ローカル(127.0.0.1等)へのアクセスまでプロキシに回されてしまい**、
自分自身が立てたテスト用サーバーにすらアクセスできない、という紛らわしい
エラーになる(外部サイトへの接続エラーと見分けがつきにくい)。

- 症状の見分け方: `curl`で同じURLを叩いても同様に弾かれるなら、
  スクリプトの不具合ではなく通信経路(プロキシ・ネットワーク制限)側の問題。
- 対処: ブラウザ起動時のオプションで、ローカルアドレスをプロキシの対象から
  除外する(「これらの宛先には直接つなぎに行く」という除外リストを渡す)。
- **代表PC上でのローカル実行では、通常こうしたプロキシは挟まらないため、
  この対処自体は不要になることが多い。** ただし同じ「原因不明の接続エラー」に
  当たったら、まず「何らかの通信経路の制限に引っかかっていないか」を疑う、
  という調べ方自体は環境によらず有効。

## 3. 承認ゲート(送信前に必ず止まる)の作り方

→ `external-action-approval-gate-pattern.md` を参照。ブラウザ操作は
「入力までは自動、送信は代表承認後」という二段階に分けるのが基本形。

## 検証の仕方

いきなり本番サイトで試すのではなく、**ローカルに簡単なテスト用ページを1つ立てて**、
入力→承認ゲートの停止→承認後の送信、という一連の流れが意図どおりに動くかを
先に確認すると、本番サイトの構造やネットワーク制限に振り回されずにロジック自体の
正しさを検証できる。
