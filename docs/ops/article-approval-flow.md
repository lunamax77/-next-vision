# 記事承認フロー（週1回・10分で回す運用ルール）

| 項目 | 内容 |
| --- | --- |
| このファイルの目的 | SEO記事を「月4本」のペースで継続公開するために、**代表が週1回・10分だけ**見ればよい承認の流れと、見るポイント・伝え方を決めたもの |
| 最終更新日 | 2026-09-07 |
| 担当 | 業務管理（ルール管理）／マーケティング（ドラフト作成）／プロダクト（HTML化・デプロイ）／代表（承認） |

---

## 1. 全体の流れ（誰が・何を・どこで）

```
 マーケ            代表              プロダクト          自動             代表
 ドラフト作成  →  10分で確認   →   HTML化して      →  デプロイ    →   公開後の確認
 docs/marketing/   「OK」or         site/ に配置       (GitHub         URLを開く
 articles/         修正指示         + sitemap更新       Actions)        Search Console
```

| ステップ | 誰が | 何をする | どこで | 承認レベル |
| --- | --- | --- | --- | --- |
| 1. ドラフト | マーケ担当 | 記事ドラフトを Markdown で作成。冒頭の枠（title／description／slug／keywords／cta／status）は既存ドラフトの形式に揃える。`status: draft（代表承認前・未公開）` で置く | `docs/marketing/articles/NN-slug.md`（NN は 01, 02… の連番。2026-09-07 時点で 01・02 あり） | L0（承認不要） |
| 2. 確認 | **代表** | 下の「5つのポイント」だけ見る。**10分で終わらなければ、その記事は「保留」でよい** | ファイルを開く（GitHub上でもチャットでも可） | — |
| 3. 承認 | **代表** | チャットで「**NN OK**」または「**NN ＋修正指示**」 | ジョブズ／マーケ担当へのチャット | **L2（公開の承認）** |
| 4. 修正（あれば） | マーケ担当 | 指示どおり直して「NN 修正しました」と報告 → ステップ2へ | 同ファイル | L0 |
| 5. HTML化 | プロダクト担当 | 承認済みドラフトをHPのデザインに合わせてHTML化、`site/` に配置、`sitemap.xml` に追加、内部リンク（トップやサービスページから）を1本以上。ドラフトの `status` を `published（YYYY-MM-DD）` に更新 | `site/blog/slug.html`（配置先の最終形はプロダクト担当が決定） | L0 |
| 6. デプロイ | 自動 | `site/` の変更が push されると GitHub Actions が自動で公開 | `.github/workflows/deploy.yml` | 代表の「OK」がここでの承認に相当 |
| 7. 公開後確認 | **代表**（5分） | 下の「公開後の確認」 | スマホ＋Search Console | — |

> **重要**：代表の「OK」は「**公開してよい**」という意味です。OKのあとは自動で世に出ます。迷う箇所があれば OK を出さず「保留」にしてください。

## 2. 代表が見る5つのポイント（これ以外は見なくてよい）

| # | 見るポイント | NGの例 | OKの目安 |
| --- | --- | --- | --- |
| 1 | **価格** | HPと違う金額、古い金額、「〜円から」の根拠がない、**税別・送料別の但し書きがない** | HPの掲載価格（税別・機材レンタル費・送料別）と一致し、但し書きがある／または価格を書いていない |
| 2 | **実績** | 実際にやっていないこと、盛った数字、出典のない「◯件」 | 本当にやったこと・本当の数字だけ |
| 3 | **社名・施設名の非掲載** | 取引先の会社名・施設名・店舗名が書かれている（HPでは非掲載の方針：`git log` の「取引先社名を非掲載に」参照） | 「関西の商業施設」「大型ショッピングモール」など**ぼかした表現**。許可を書面でもらった先だけ実名可 |
| 4 | **写真の顔** | お子様・来場者の顔がそのまま写っている | モザイク済み、後ろ姿、スタッフのみ、または写真なし |
| 5 | **言い切り表現** | 「必ず集客できる」「絶対安全」「日本一」「最安」など、根拠がない断定・最上級 | 「〜を目指せます」「〜の実績があります」「安全に配慮して運営」など |

補足：誤字脱字・文章のうまさ・SEOの良し悪しは**代表は見なくてよい**（マーケ担当とプロダクト担当の責任範囲）。

## 3. 承認の伝え方

チャットで一言。**記事番号＋判定**の形で。

| 伝え方（例） | 意味 |
| --- | --- |
| `01 OK` | そのまま公開してよい |
| `02 3段落目の価格を修正` | 指摘箇所を直したら、再確認なしで公開してよい（**軽微な修正**） |
| `02 3段落目の価格を修正 → 再確認` | 直したあと、もう一度代表が見る（**大きめの修正**） |
| `03 保留` | 今週は判断しない。理由は書かなくてよい |
| `04 NG 理由: ◯◯` | 公開しない。ボツ、または大幅に作り直し |

- 指示は短くて構いません。「どこ（段落・見出し）」＋「何を（価格／表現／写真）」があれば十分です。
- 「修正」だけで「→ 再確認」がなければ、担当は直してそのまま公開に進みます。**もう一度見たいときは必ず「→ 再確認」を付けてください。**

### `<!-- 要確認 -->` コメントの扱い

マーケ担当は、自分で判断できない箇所（価格・実績の数字・実名の可否など）に **`<!-- 要確認: ◯◯ -->`** という印を入れます。

- 代表は **`要確認` を検索して、その箇所だけ答える**でOKです（例：「01 要確認1: 税込で正しい。要確認2: 施設名は出さない」）。
- **`要確認` が1つでも残っているドラフトは公開しない**（プロダクト担当はHTML化しない）ルールです。
- 代表の回答をもとにマーケ担当が本文を確定し、印を消してから承認に進みます。

## 4. 公開後の確認（代表・5分）

1. **URLをスマホで開く**：記事が表示される／画像が出る／リンクが切れていない。表示崩れがあればスクリーンショットをプロダクト担当へ。
2. **Search Console に伝える**：https://search.google.com/search-console/ を開き、上部の検索窓（URL検査）に記事URLを貼る → **「インデックス登録をリクエスト」**。これでGoogleに早く見つけてもらえます。
   - sitemap.xml はプロダクト担当が更新しているので、忘れても数日で自動的に拾われます。必須ではありませんが、やると早い。
3. **HP内の導線**：トップページなどから記事へのリンクが1本以上あることを確認（プロダクト担当の作業。代表はクリックして飛べるか見るだけ）。

## 5. 週次スケジュール（例）

マーケ担当のカレンダー（`docs/marketing/content-calendar.md`）は「公開は火曜または水曜」で組まれています。それに合わせた例です。

| 曜日 | 誰が | 何を |
| --- | --- | --- |
| 前週の木〜金 | マーケ担当 | 翌週分のドラフトを `docs/marketing/articles/` に置き、「NN ドラフト完了、要確認 X 箇所」とチャットで報告 |
| **月（or 代表の都合のよい曜日）** | **代表** | **10分**：`要確認` に答える → 5つのポイント確認 → 「NN OK / 修正 / 保留」 |
| 火 | プロダクト担当 | HTML化 → push → 自動デプロイ → 「NN 公開しました URL: …」と報告 |
| 水〜 | 代表 | 公開後の確認（5分） |

代表が見る曜日は固定しておくと続きます。**要確認：何曜日にしますか？**（本ファイル末尾）

## 6. ペースが崩れたときの優先順位ルール

目標は **月4本（週1本）**。崩れたときは次の順で判断します。

1. **まず、質より「止めないこと」を優先する**：1本の完成度を上げるより、承認できる記事を先に出す。見直しは公開後でもできます（修正して再デプロイすればよい）。
2. **代表の時間がない週**：保留にしてよい。ただし **2週続けて保留になった記事は、マーケ担当が「要確認」を減らす（自分で判断できる無難な内容に書き直す）**。代表の負担を増やさない方向で解消します。
3. **ドラフトが間に合わない週**：マーケ担当は「今週なし」と報告。**翌週に2本まとめて出すのは可**。代表の確認時間は 20 分に増えます。
4. **月末で 4本に届かない**：無理に本数を追わない。月次レビュー（`docs/ops/roadmap-2026q4.md`）で「なぜ届かなかったか」を1行で残し、翌月の本数目標を **3本** に下げてよい。目標を下げるのは代表判断。
5. **本数より優先するもの**（これがある週は記事を後回しにしてよい）
   - 問い合わせ対応（`docs/ops/inquiry-handling-rules.md`）
   - サーバー・フォーム等の**障害対応**
   - 代表の**商談・現場**
6. **絶対に崩さないもの**：5つのポイント（特に社名非掲載・写真の顔・言い切り表現）。急いでいても、これを飛ばして公開はしない。

## 7. テーマの決め方（参考）

- テーマ・キーワードの候補出しはマーケ担当の仕事（L0）。代表は「このテーマは書かないで」（NGテーマ）だけ指定すれば足ります。
- 3か月・12本の予定はマーケ担当がすでに `docs/marketing/content-calendar.md` に置いています（第1月：基礎記事、第2月：商材別、第3月：業種別・比較）。キーワードの根拠は `docs/marketing/seo-keywords.md`。代表が承認するのは**記事1本ずつ**で、カレンダー全体の承認は不要です（順番を変えたいときだけ一言ください）。
- 参考：`docs/marketing/01-sns-strategy.md` のコンテンツの柱（こども免許証／ワークショップ／エア遊具／運営代行の裏側／実績／豆知識）と同じ柱なので、SNSと相互に使い回せます。

## 要確認事項（代表の判断が必要）

1. **代表が記事を見る曜日**：何曜日に固定しますか？（案：月曜。公開が火・水のため）
2. **軽微な修正は再確認なしで公開してよいか**：本ファイルでは「修正指示のみ＝再確認なしで公開」としています。すべて再確認したい場合は教えてください（その場合、週の所要時間は 15〜20 分になります）。
3. **実名掲載の基準**：取引先名は「書面で許可をもらった先だけ実名可」でよいですか？ 口頭許可でも可にしますか？
4. **記事の配置先URL**：`https://nextvision.fun/blog/…` の形で問題ないか（プロダクト担当が提案 → 代表承認）。
